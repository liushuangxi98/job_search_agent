## 1. 目的、范围与成功标准

### 1.1 求职和学习目标（已确认）

用户有四年 Python 自动化测试开发经验和 Agent 学习经验，目标岗位为 **Python Agent 应用开发**。通过亲手实现这个项目，获得开发、解释、测试和排查 Agent 应用的能力；通用前后端工程不作为主要学习方向。

产品输入为一份简历、求职条件、人工导入的岗位资料及本地 Markdown 题库，输出岗位评估和投递比较报告，并提供基于岗位的文字模拟面试及聊天补充入口。

成功有两层，分别验收：

1. **应用支撑可用**：前端、FastAPI、MySQL 和接口可运行，能用明确标注的固定样例联调。这不表示 Agent 已实现。
2. **Agent 能力完成**：用户实现的代码接入真实模型、知识库和工具，完成业务闭环、行为评测及故障排查。仅有演示样例不算通过。

### 1.2 运行边界（已确认）

- Windows 本机、单用户运行，不作公网交付。
- 保留简历解析与确认、岗位截图导入、岗位池、材料勘察、匹配与通勤评估、总分报告、题库、模拟面试、聊天、记忆、工具轨迹和评测。
- 不做爬虫、岗位自动发现、多用户、多 Agent、语音面试、云端图片识别、自定义评分权重或基于不匹配条件的强制淘汰。
- 任务进度不持久化，不做跨服务重启的断点恢复。已确认业务资料和已完成结果仍保存。
- 模型可用自身知识补充分析与建议；有材料时提供引用，不编造来源。面试方向统一说明“依据 JD 推测”，不包装成公司的真实面试记录。

### 1.3 Agent 的实际决策空间

外层业务步骤固定，内层模型根据观察结果选择工具、检索词、追问或结束时机。程序负责校验、预算、计算和保存。

保留的自主决策包括：简历要不要澄清；先评估哪些材料较完整的岗位；证据不足时如何改写查询；地址歧义时向用户询问；面试下一题、追问和难度；聊天意图及资料变更提案；自检失败后的一次修复。

不以“相同输入随机出现不同路径”证明 Agent 能力。验收重点是：关键材料或回答变化后，决策是否合理变化；相同条件下，关键结论是否合理稳定。

## 2. 方案选择与代码归属

### 2.1 已选方案

| 部分 | 选择 | 作用 |
| --- | --- | --- |
| 前端 | 原生 HTML、CSS、JavaScript | 单页界面，按功能分文件 |
| 应用后端 | FastAPI | 页面服务、HTTP 接口、文件和数据存取 |
| Agent | LangGraph + 普通 Python 业务函数 | 状态、工具循环、人工补充和业务决策 |
| 业务数据库 | MySQL | 画像、条件、岗位、题库元数据、已完成报告 |
| 向量索引 | 本地 Chroma | 资料与题目的向量检索 |
| 聊天模型 | DeepSeek | 对话、抽取、工具调用、判断与解释 |
| Embedding | 百炼 | 文档和查询向量化 |
| 重排 | 百炼专用重排模型 | 对召回候选重新排序 |
| 通勤 | 高德地图 API | 公共交通和驾车路线 |
| 招聘截图识别 | 本地 MCP OCR | 原图留在本机，识别文字交给模型 |

考虑过 Vue 前端：它提供组件与状态组织方式，但增加了用户需要理解的前端概念。用户选择原生前端，保留必要的页面分工和路由。FastAPI 可以同时提供静态页面与 API；Chroma 可在本机目录保存索引。[FastAPI 文档](https://fastapi.tiangolo.com/tutorial/static-files/)、[Chroma 文档](https://docs.trychroma.com/docs/run-chroma/clients)

不引入独立前端开发服务器、微服务、消息队列或额外的工作流平台。具体依赖版本在实现前检查兼容性并锁定；当前没有依赖安装或兼容性验证结论。

### 2.2 谁写哪些代码（已确认）

**用户亲手编写全部 Agent 相关代码。** Codex 提供设计说明、接口约定、讲解、排错建议和代码审查；除非用户以后明确改变分工，不替用户填入 Agent 实现。

| Codex 实现 | 用户实现 |

| FastAPI 路由和请求格式校验 | LangGraph 编排、工具调用循环及治理 |
| 文件上传、保存、按文件 ID 读取 | 简历和 MD 正文解析、OCR MCP 调用、岗位抽取 |
| MySQL 表结构、连接、普通增删改查 | Embedding、Chroma、混合检索、重排与查询改写 |

数据库 CRUD 只负责存取；记忆是否成立、哪些事实进入上下文等规则归用户。后端可以校验结果结构和数值范围，但不另写一份业务评分算法。通用日志可以保存事件，工具选择、调用计数、重试决策和事件生成归用户。

联调样例只返回固定数据，不包含替代性的 Agent 算法。界面明确显示“模拟数据”；真实模式未接入时明确报“Agent 尚未接入”，不静默返回样例。

## 3. 模型接入约定（已确认）

- 聊天采用 OpenAI 兼容的 Chat Completions 格式；Embedding 采用 OpenAI 兼容的 Embeddings 格式。
- 每项配置包含 **URL、Key、Model**。模型名可以预设，首次使用补 URL 和 Key；换型号时修改 Model。
- 百炼专用重排是协议例外，用独立适配函数调用其 HTTP API，仍使用 URL、Key、Model 配置。
- 不把业务逻辑绑定到供应商 SDK；第三方工具调用、JSON 输出等能力要针对实际型号验证，不能仅凭“兼容”二字认定全部参数可用。
- API Key 放本地环境配置，不进入前端、日志、报告或版本库。所有模型接入代码由用户实现。

聊天和 Embedding 请求都需要模型标识；百炼重排请求使用自己的 `input.query`、`input.documents` 等结构。[聊天协议](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[Embedding 协议](https://developers.openai.com/api/reference/resources/embeddings/methods/create)、[百炼重排协议](https://help.aliyun.com/zh/model-studio/text-rerank-api)

具体型号、服务区域和模型费用尚未确定。设计不承诺只换任意 URL、Key 就能跨供应商无差别运行，也不预先替用户选择付费调用档位。

## 4. 业务流程

### 4.1 简历与求职条件

1. 上传 DOCX 或文本型 PDF；后端保存文件，用户实现正文解析和画像提取。
2. 在可编辑表单展示画像及原文依据，用户确认后用于评估。聊天补充的事实记录为用户确认内容，不伪造简历原文。
3. 信息完整时不提问；起步澄清最多三个与求职相关的问题。仍缺失的内容列为待补充。
4. 填写城市、岗位方向、期望税前月薪区间、通勤起点、可接受单程时间及常用出行方式。
5. 程序拒绝非法数值、反向区间等格式错误；城市、薪资、经验等不匹配不构成岗位自动淘汰条件。

**设计默认：**当前只维护一份有效画像和一份求职条件。采用一张表单统一确认，不增加逐字段审批流程。扫描型 PDF 暂不支持，提示换文本型 PDF、DOCX 或补充文字。

### 4.2 截图导入岗位池

固定流程为：**上传 → 本地 OCR 一次 → 模型提取一次 → 预览修改 → 确认入池**。

- 一张截图可包含多个岗位，列表页、详情页和长截图均可尝试识别。
- 原图留在本机；OCR 得到的招聘文字可以发给模型。
- 保留原图、OCR 文本和岗位来源关系。OCR 置信度是文字识别置信度，不宣称它等于岗位字段准确率。
- 取消自主裁切和反复识别循环。失败时可手动粘贴、修改或重新上传。
- 所有提取结果先预览再确认；缺失和明显异常的字段可提示，不增加复杂置信度分类系统。
- 重复岗位不重复入池，合并后保留多个来源。

**设计默认：**精确重复原图或标准化原文可直接识别为重复；公司、职位、城市、工作地址一致的记录提示复用。字段缺失时只提示可能重复，由用户决定，避免误合并不同团队或地点的岗位。

**设计默认：**前端可选多张图，但逐张上传和处理；图片单文件初始上限 8 MiB，简历和 MD 单文件初始上限 16 MiB。按实际请求字节数限制体积，任何请求体不得超过 48 MiB。413 使本轮操作失败，不自动重试同一请求。Token 统计用于上下文与费用，不能代替字节大小检查。

### 4.3 材料勘察与岗位评估

- 资料来自用户导入或聊天补充；不自动联网搜索公司或面经。
- 根据简历、JD 和已有材料检查可评估内容及缺失项。公司资料或实际面经缺失，不阻止已有依据的匹配评估。
- 面试准备采用“JD 推测能力点 → 本地题库检索”，不是生成所谓真实公司面经。
- 模型可在预算内决定先处理哪些岗位、检索什么、是否改写查询、是否需要用户补充、何时停止。
- 未处理完或资料不足的岗位仍在岗位池中，说明原因；不因为预算或匹配程度自动删除。
- 程序计算分数并核验引用；模型写分析、缺口和投递建议。

单项缺失时保留其他有依据的结果。例如地址不明确只影响通勤；题库覆盖不足只影响该方向的面试准备。必要计分数据缺失则总分为空，不用零代替未知。

### 4.4 通勤

- 同一出发地址分别查询高德公共交通和驾车的**单程**方案，均展示预计时间、距离和主要路线。
- 常用方式默认公共交通，可切换为驾车。所有岗位统一使用该方式计算通勤分，不自动选择两种方式中更快的一种。
- 地址有多个合理候选时请求用户确认，不直接将公司名猜成具体办公地址。
- API 失败、无路线或关键耗时缺失时显示未知，不能填 0。
- 保存用于报告的查询时刻、已确认地址、交通方式、耗时及距离，便于解释当时结果；历史报告不承诺反映最新路况。

**设计默认：**每种方式展示高德返回的首个符合请求条件的推荐方案；时间统一转换为分钟、距离统一转换为千米。内部保留原始单位和值，显示舍入不改变算分依据。首版采用请求时返回的估算，不增加未来早晚高峰预测功能。

高德提供公交和驾车路线接口，接入参数与返回单位按实际采用版本核验。[高德路线规划文档](https://developer.amap.com/api/webservice/guide/api/newroute)

### 4.5 固定评分与统一排序

**已确认：**所有分数为百分制；总分为 `0.60 × 匹配分 + 0.25 × 薪资分 + 0.15 × 通勤分`。无自定义权重，不按类别分别排名。

#### 匹配分（已确认）

将 JD 要求逐项对应到简历或用户确认的材料：明确支持记 1，部分支持记 0.5，未找到证据记 0。各项等权平均后乘 100。

要求、对应证据和覆盖判定随结果保存。模型负责提出对应关系，程序负责计算。未找到证据不等于用户不会；分数不代表录用概率。

**设计默认：**重复要求合并后计分；没有可识别要求时匹配分为空。可复算指对已保存的要求和判定能得到相同算术结果，不要求模型多次抽取完全一致。

#### 薪资分（设计默认，待整体确认）

只比较已确认的税前固定月薪区间，以区间中点作比较值。令岗位中点为 `J`、个人期望中点为 `E`，均须大于 0：

`薪资分 = 100 × min(J / E, 1)`。

例如期望 20—30K、岗位 18—22K，中点分别是 25K 和 20K，薪资分为 80。高于期望中点封顶 100。奖金、股票、第几薪保留文字说明，不猜测折算；仅有年薪或“面议”等不能直接比较的材料时，等待用户确认月薪口径。

#### 通勤分（设计默认，待整体确认）

令常用方式单程时间为 `t`，个人可接受单程上限为 `L`，二者均以分钟计，`L > 0`：

| 单程时间 | 通勤分 |
| --- | ---: |
| `t ≤ 0.5L` | 100 |
| `0.5L < t ≤ L` | 80 |
| `L < t ≤ 1.5L` | 50 |
| `t > 1.5L` | 20 |

这是固定的偏好量化规则，超过上限只降低分数，不淘汰岗位。查询失败或所选方式无有效结果时通勤分为空，即使另一方式有结果也不自动替换。

#### 排序和缺数据

- 三个分数齐全才计算总分；不重新分配缺失项权重。
- 总分降序，缺总分岗位在同一列表末尾标记待补充，不另开分类排名。
- 少于两个总分完整的岗位时展示分数和建议，不宣布相对名次。
- **设计默认：**相同总分按岗位 ID 稳定展示；计算保留精度，最后展示一位小数。
- 算例：匹配 80、薪资 100、通勤 80，总分为 `48 + 25 + 12 = 85`。

### 4.6 自检、报告与导出

程序检查引用是否存在、数值范围、计算结果与状态是否一致。失败时给模型一次修复机会；仍失败则保存可用部分和错误说明，不宣称结果完整。

岗位比较报告包含统一总分表、分项依据、技能差距、通勤、待补充信息和投递建议。引用指向真实资料，模型补充知识不生成虚构出处。

**设计默认：**导出 Markdown 和 JSON；首版不增加 PDF/Word 排版。保存报告时包含输入快照、证据、分项判断、公式版本及模型标识，以便复算。用户后续修改资料不会覆盖历史报告，界面提供重新评估入口。

### 4.7 MD 题库与 RAG（已确认）

用户提供 Markdown 题库，用户自己实现解析。基础链路为解析、分块、向量化、检索和引用；增强链路包括关键词与向量混合检索、重排、检索不足时改写查询再检索。

- 以题目作为优先组织单位，保留原始文件、题目 ID、原文位置、题干、参考答案及知识点信息。
- 不预先假定用户 MD 完全符合某个模板；拿到实际样例后确定解析规则。无法识别的内容明确报告，不把普通段落自动冒充已有题目。
- 支持批量导入、去重及知识点覆盖统计；覆盖统计说明本题库已包含什么，不宣称覆盖全部 Agent 面试知识。
- 用户更新或删除资料时，同步维护对应索引及来源状态，旧报告的已保存证据快照继续可读。
- 基础版和增强版使用同一组标注案例比较效果、耗时和调用量，不预设增强一定更好。
- MySQL 保存资料和题目元数据，Chroma 保存向量；通过稳定 ID 对应，索引可以从原始资料重新构建。

**设计默认：**初始向量召回与关键词召回各取最多 10 条，去重后最多 20 条参与重排，返回最多 5 条证据；同一需求最多改写重检索一次。参数放单一配置文件，实验时可改，不增加页面调参面板。

### 4.8 模拟面试

从岗位详情进入面试间，依据 JD 与简历决定考点，主问题来自题库，可作岗位化改写。追问可以生成，但记录原题 ID、考点和追问原因，明确是基于原题的衍生追问。新的独立考点需要重新检索；无题库覆盖时提示，不虚构主问题和来源。

**已确认：**最多八轮问答，追问也占一轮；一问一答，用户或模型可以提前结束。无倒计时，结束后统一反馈，不逐题即时讲解答案。

面试报告包括能力维度评分、回答证据、薄弱项和推荐练习。

**设计默认（待整体确认）：**

- 每道主问题有一个主要考点；主问题及其追问作为一组评价，避免追问越多该题权重越大。
- 模型依据题库参考答案、用户回答和通用知识给出 0—4 分：0 为回答无法体现该考点，1 为明显不足，2 为部分掌握，3 为基本正确，4 为正确且解释充分。
- 该维度得分为所属题组分数平均后换算为百分制；尚未考察的维度显示未考察，不记 0。
- 主动回答“不会”可以据此评价；未提交回答或跳过的题不作为零分计入。
- 题库缺参考答案时可用模型知识反馈，但评语注明“未提供参考答案，本题为模型反馈”；不虚构参考答案出处。评分是练习反馈，不作为岗位总分的一部分。
- 推荐练习优先引用已有题库条目，无覆盖时给学习方向。

### 4.9 聊天与记忆

聊天是必要入口，在简历、条件、岗位、评估和报告阶段均可打开。发送时明确关联当前对象，避免把 A 岗位的信息写进 B 岗位。

- 普通解释直接回答；补充资料时由模型生成变更摘要，用户一次确认后保存。
- 可补充画像、求职条件、岗位 JD 或地址。保存后提供重新评估入口，历史报告不自动重写。
- 长期记忆以用户确认的画像、偏好和有答题证据的薄弱项为主，可纠正、更新和删除。
- 画像与偏好变更先确认；薄弱项来自已完成面试报告并绑定答题证据，用户可修正。
- 只加载当前任务相关的画像、资料、记忆和有限对话上下文。

**设计默认：**普通聊天逐条历史、未确认提案、当前面试进度及上下文摘要仅在内存；已确认变更和已完成面试报告进入 MySQL。报告内保存必要问答证据。需要资料确认时允许本次运行暂停等待，同一服务进程内可继续；服务重启后未完成交互重新发起。

## 5. Agent 与应用的接口边界

本节是接口设计，不是 Agent 实现。具体字段类型和端点名称由 Codex 在后续前后端计划中落实，并与用户编写的 Agent 入口对接。

### 5.1 最小调用面

| 能力入口 | 输入要点 | 输出要点 |
| --- | --- | --- |
| 解析简历 | 上传文件 ID | 画像草稿、出处、最多三个澄清问题 |
| 提取岗位 | 图片或手动文本资料 ID | 岗位草稿列表、来源、待补字段 |
| 索引题库 | MD 资料 ID | 题目/分块元数据、索引与覆盖结果 |
| 评估岗位 | 岗位 ID 列表、画像和条件快照 | 分项依据、分数、通勤、缺失项、报告 |
| 开始/继续面试 | 岗位、会话 ID、回答 | 下一题或结束报告 |
| 聊天 | 消息、当前对象、当前会话 | 回答或待确认的资料变更提案 |
| 提交人工补充 | 运行 ID、问题/提案 ID、确认内容 | 继续运行或结束状态 |

Agent 通过后端提供的资料读取、结果保存和事件发送接口工作，不直接依赖 FastAPI 请求对象。后端通过一个明确的 Agent 调用入口交接，不为每个模型建立一套应用层框架。

### 5.2 运行状态与事件（设计默认）

运行状态采用 `running / needs_input / completed / partial / failed`。它们描述一次运行，不能替代“某字段缺失”“索引失败”等具体业务信息。

事件至少能表达：状态变化、工具开始/结束、结果摘要、耗时、预算用量、请求人工输入、最终结果或错误。前端展示执行事实与简短理由，不依赖模型供应商的隐藏推理字段。

后端为事件提供通用传输和查看功能；Agent 决定发出哪些事件。完成结果先经过输出结构校验再保存；画像或岗位变更必须走确认后的 CRUD，不能让模型直接提交 SQL 或任意数据库字段更新。

### 5.3 最小运行约束（设计默认）

- 一次只运行一个需要模型的活动，避免引入多任务调度；页面查看、资料编辑不受影响。评估处于 `needs_input` 时，聊天/确认入口用于当前活动的补充。
- 每批最多 10 个用户选中的岗位，逐岗评估；超出时分批发起，不淘汰剩余岗位。
- 每岗初始预算为模型请求最多 8 次、工具调用最多 12 次；结构修复和重检索也占预算。单次模型请求超时初设 60 秒，普通工具超时初设 30 秒。
- 超预算即返回已取得的部分结果。为形成最终说明可以使用程序模板，不在耗尽预算后继续调用模型。
- 未知工具、参数不合法或越权操作在执行前拒绝。可恢复的网络/限流错误最多重试一次，并遵守返回的重试提示及剩余预算；413 不重试并使整轮失败。
- 工具结果缓存仅在本进程内，缓存键包含实际输入条件，避免重复调用；不承诺服务重启后保留。

这些是便于起步的内部参数，用户实现 Agent 时可依据评测调整并记录，不能无限循环。月度金额预算、每周投入时间和完成日期尚未指定，不将这些初始次数等同于费用保证。

## 6. 数据与前端

### 6.1 存储职责

| 存储 | 内容 |
| --- | --- |
| MySQL | 当前画像与条件、岗位、资料元数据、题目元数据、已确认记忆、已完成评估和面试报告 |
| 项目本地文件 | 上传原文和图片、导出文件、执行日志 |
| Chroma 本地目录 | 文档/题目向量及检索元数据 |
| 内存 | 未完成运行、等待确认的提案、当前聊天和面试上下文、临时缓存 |

**设计默认：**报告以 JSON 保存完整结果及输入快照，常用查询字段单独建列；不为每个模型输出字段创建一套复杂关系表。当前画像/条件带简单修订标识，报告可据此提示资料已变化。数据库支持持久化不意味着任务可断点恢复。

文件接口接收资料 ID，由后端解析为项目内文件路径，不让前端或模型指定任意本机读取路径。用户自己的文档解析代码通过该受控读取接口取得内容。

### 6.2 前端流程（已确认）

- 一个 HTML 入口，左侧步骤导航：简历、条件、岗位池、评估、报告、题库。
- 主视图切换；岗位列表为表格，详情在抽屉中展示，保留当前筛选、选择与滚动位置。
- 评估页面显示逐岗状态与执行轨迹，人工补充入口就地出现。
- 面试为全屏视图，隐藏步骤导航，结束后回到岗位详情。
- 右下角聊天抽屉保留，显示当前关联对象及待确认修改。

**设计默认：**使用简单 hash 路由实现后退和深链接。页面刷新后重新读取已保存业务资料；若当前进程仍保有运行 ID，可继续查看该运行。运行已丢失时提示重新发起，不宣称恢复了丢失的任务。聊天忙碌时显示当前活动状态，不并发开启另一个模型活动。

视觉样式在前端实现阶段用少量页面样例确定，不引入组件库。视觉验收由子代理进行，父线程只接收文字结论；一次仅截必要区域的一张图，完成后关闭子代理。

### 6.3 文件组织（设计默认）

- `frontend/`：页面、样式、API 调用和少量视图模块，Codex 实现。
- `backend/`：路由、数据契约、数据库与存取、Agent 接口适配、固定联调样例，Codex 实现。
- `career_agent/`：用户创建并实现的 Agent 包，独立于 FastAPI；按需要拆分模型、编排、工具、RAG、记忆和业务模块。
- `tests/`：按前后端与 Agent 分开职责；Agent 测试由用户实现。
- `data/`：上传、索引、导出和日志，不入版本库。
- `docs/`：设计、接口约定和学习/验收说明。

不照搬参考目录中的大量占位文件，也不因参考目录写有“已实现”而认定本项目已经具备相应能力。

## 7. 验收与分阶段交付

### 7.1 更新后的需求验收

| 编号 | 验收标准 |
| --- | --- |
| R1 | 简历画像可编辑确认，有原文或用户补充依据；未确认画像不进入评估 |
| R2 | 完整资料不提问，起步澄清最多三个问题 |
| R3 | 非法输入在模型调用前拒绝；合理但不匹配的求职偏好不触发强制淘汰 |
| R4 | 单图可提取多岗位；一次 OCR、一次提取后人工预览；去重、来源追溯和手动回退有效 |
| R5 | 各岗显示材料缺失；按维度提供部分结果；不因缺公司面经阻断匹配 |
| R6 | 保存要求、覆盖判定和证据后可复算匹配分；引用有效；无题库覆盖不编造主问题 |
| R7 | 公交和驾车均支持；同一常用方式参与评分；歧义确认、单位换算、失败不填零 |
| R8 | 错误引用/越界分数能被检测；模型最多修一次，失败返回部分结果或明确错误 |
| R9 | 总分固定为 60/25/15；同表统一排序；缺项不填零；少于两份完整总分不宣布排名 |
| R10 | 用户 MD 可导入、去重、检索、更新和删除；覆盖统计和引用对应真实内容 |
| R11 | 最多八轮含追问；主问题有题库来源，衍生问题关联原题；证据/回答改变时路径合理变化 |
| R12 | 面试报告包含维度反馈、答题依据、薄弱项、练习建议；未考察不记零 |
| R13 | 工具白名单、参数、预算与错误处理生效；调用有轨迹；413 不自动重试 |

| R15 | 聊天可补充当前对象资料；确认后保存，拒绝则不修改；旧报告不静默重写 |
| R16 | 已确认资料及完成结果重启后存在；未完成任务不恢复，界面明确区分 |
| R17 | 真实模式和模拟联调模式明确区分，Agent 未接入不会被固定样例伪装为成功 |

### 7.2 评测证据

用户编写 Agent 评测代码，至少覆盖工具选择、错误参数、预算耗尽、地址歧义、无检索结果、一次重检索、自检修复、回答变化后的面试决策，以及聊天修改确认/拒绝。

RAG 比较记录检索命中与排序指标、引用有效性、延迟和调用量。分开用于调整的案例与保留验证的案例，不用调过参数的同一批结果证明泛化。

**设计默认：**以约 30 条人工标注检索案例作为起步规模，覆盖精确术语、同义表达和无答案输入；真实端到端联调至少覆盖一份简历、三个岗位、公交/驾车查询、一份 MD 题库和一次含追问的面试。案例规模只是起点，不代表统计充分性。

Codex 负责前后端参数校验、存取、页面交互及接口联调的测试。所有完成结论注明使用的是固定样例还是真实服务、Agent 是否由用户实际实现、有哪些未验证范围。

| 阶段 | 主要交付 | 负责人 | 验证 |
| --- | --- | --- | --- |

| D1 应用支撑 | 前端、FastAPI、MySQL、接口契约、固定样例 | Codex | 可启动、CRUD 与页面流程通过；明确仍为样例 |

| D3 资料链路 | 简历解析、OCR 客户端、岗位提取、画像确认与读取 | 用户 | 真实资料能进入已实现的界面与数据库 |

## 9. 整体确认时重点核对

访谈决定均已记录。本文新增的主要设计默认如下，确认文档时可以直接修改这些规则：

1. 薪资按固定月薪区间中点相对期望中点计分；通勤按个人上限的四档计分。
2. 面试按主问题及追问成组打 0—4 分，再聚合为能力维度分。
3. 一份当前画像/条件；普通聊天和未完成面试只留内存；完成报告保存必要问答和输入快照。
4. 每批岗位、模型/工具次数、一次重检索、上传大小等内部初始上限。
5. Markdown/JSON 导出、hash 路由及约 30 条检索评测案例的起步规模。

这些默认规则不增加用户设置页面，不改变“用户亲手实现全部 Agent 代码”的分工。
